# CoEvolution Hub Dashboard (T6.1)

The **CoEvolution Hub Dashboard** is the main graphical entry point of the CoEvolution framework. It is a single web interface through which users interact with the CoEvolution Hub. From it, users access information about AI models, reports, assessment results and other outputs produced by the integrated components.

The Dashboard is one of the five components of the **CoEvolution Hub**, developed in **WP6 / Task 6.1**. The other four are the Orchestrator, Communication Infrastructure, User and Credential Management, and Knowledge Base. The Dashboard is documented in deliverable **D6.2, *A minimum viable product of the integrated framework to be validated and demonstrated*** (Section 3.1.1, Table 3).

> **Part of:** CoEvolution Hub (WP6 / T6.1) · **Type:** Frontend (Angular SPA) · **Responsible partner:** AEGIS IT Research

## Functionality in the MVP

The Dashboard is the user-facing interface for the main activities of the CoEvolution model lifecycle:

- **Model registration and version management.** Users enter model metadata (name, type, paradigm, architecture family, framework, input modality, version) and upload the `requirements.zip` dependency list.
- **Model monitoring.** Users see registered models, their reports and assessment results in the Monitoring View.
- **Report upload.** Users upload the reports of externally executed tools:
  - assessment and defence reports, which are combined into the updated risk report;
  - the additional evidence reports: **AIMODELINFO**, **Gadgets**, **Regulatory** (EU AI Act) and **Datasets**.
- **Tools.** Users interact with the registered gadgets, data generators, and assessment and defence tools.
- **AIMBOM generation.** Users trigger generation of the AI Model Bill of Materials once the required evidence is available.
- **Trusted model registration.** Users upload the trusted model once the assessment and assurance evidence has been generated.
- **Runtime monitoring.** The SRME user interface is embedded in the Dashboard.

The Dashboard is based on the **Advanced Visualisation Toolkit (AVT)** of [AEGIS IT Research](https://aegisresearch.eu/). See the [AVT website](https://avt.aegisresearch.eu/).

## Architecture and interfaces

```
                        ┌──────────────────────────────┐
  User (browser) ─────▶ │  Hub Dashboard  /fvt/        │
                        │  Angular SPA served by Nginx │
                        └───┬──────────┬───────────┬───┘
            OIDC login      │          │ REST      │ iframe
            (JWT)           ▼          ▼ + Bearer  ▼
              ┌──────────────────┐  ┌──────────────────┐  ┌──────────┐
              │ User & Credential│  │ Orchestrator     │  │ SRME UI  │
              │ Management       │  │ /api/v1          │  │          │
              │ (Keycloak)       │  └────────┬─────────┘  └──────────┘
              └──────────────────┘           │
                               MongoDB · MinIO (Knowledge Base) · Kafka → engines
```

**Design principles (from D6.2):**

- **Single backend interface.** The Dashboard **does not access the Knowledge Base databases or object storage directly**. All model-related reads and writes go through the **Orchestrator REST API** (`/api/v1`). The Dashboard therefore stays independent of the MongoDB and MinIO storage underneath.
- **Delegated authentication.** Users log in through the User and Credential Management component (Keycloak), which issues a signed JWT. The Dashboard attaches this token as a **Bearer token** to every Orchestrator request. The Dashboard never stores or checks passwords.
- **Embedded partner UIs.** Partner interfaces such as SRME are loaded in an iframe inside the Dashboard shell.

**Example interaction: model registration (D6.2 Section 4.2).** A single form submission results in two sequential Orchestrator calls:

1. `POST /api/v1/models/register`: the model metadata. The response returns the new `model_uuid`.
2. `POST /api/v1/files/upload`: the `requirements.zip` archive, tagged with the `model_uuid` and version. The Orchestrator then notifies RAGRE through Kafka.

The full list of Orchestrator endpoints is in the [Swagger documentation](https://aegis.coevolution-project.eu/api/docs).

## Configuration

Configuration is supplied **at runtime** through environment variables. The container writes them into `assets/env.js` at startup, so the same image runs in any environment without being rebuilt. On Kubernetes they come from the `fvt-config` ConfigMap.

| Variable | Required | Description |
| --- | --- | --- | --- |
| `SERV_HOST` | Yes | Base URL of the Hub backend (Orchestrator) | 
| `API_URL` | Yes | API path prefix of the Orchestrator | 
| `KEYCLOAK_URL` | Yes | Base URL of the User and Credential Management (Keycloak) server | 
| `SRME` | Yes | URL of the SRME user interface loaded in the iframe | 
| `SOCKET_HOST` | No | Reserved for real-time updates (see [Roadmap](#roadmap)). Not used in the current version. | 

API requests are sent to `SERV_HOST` + `API_URL`, for example `https://aegis.coevolution-project.eu/api/v1/models/register`.

All URLs are opened **by the user's browser**, so they must be publicly reachable addresses, not cluster-internal service names. The Dashboard is served over HTTPS, so the `SRME` URL must also use **HTTPS**. Otherwise the browser blocks the iframe as mixed content.

## Deployment on Kubernetes

The Dashboard is deployed as a container in the CoEvolution Kubernetes infrastructure, together with the other Hub components. The manifests in `k8s/` define four resources:

| Resource | Name | Purpose |
| --- | --- | --- |
| ConfigMap | `fvt-config` | Runtime configuration (see [Configuration](#configuration)) |
| Deployment | `fvt` | One replica of `ghcr.io/coevolution-project-eu/coevolution-dash:latest` on port 80, with readiness and liveness probes on `/fvt/` |
| Service | `fvt` | ClusterIP service on port 80 |
| Ingress | `fvt` | Routes `https://<host>/fvt` to the service |

### Steps

**1. Set the configuration.** Edit the `fvt-config` ConfigMap in `k8s/` with the URLs of your environment.

**2. Set the host.** Replace `dashboard.example.com` in the Ingress with your domain. For HTTPS, add a `tls:` section with a certificate Secret, and set `ingressClassName` if your cluster has more than one Ingress controller:

```yaml
spec:
  ingressClassName: nginx
  tls:
    - hosts: [<your-domain>]
      secretName: <tls-secret>
```

**3. (Optional) Pin the image version.** The manifest uses `:latest` with `imagePullPolicy: Always`, so each restart pulls the newest build. For a reproducible deployment, use a fixed tag instead.

**4. Deploy:**

```bash
kubectl apply -f k8s/
kubectl rollout status deployment/fvt
kubectl get pods,svc,ingress -l app=fvt
```

**5. Open** `https://<your-domain>/fvt/`.

For quick testing without an Ingress:

```bash
kubectl port-forward svc/fvt 8080:80
```

Then open **http://localhost:8080/fvt/**.

**Applying configuration changes.** Pods read the ConfigMap only at startup. After editing it, restart the deployment:

```bash
kubectl apply -f k8s/
kubectl rollout restart deployment/fvt
```

## Running locally

### With Docker (published image)

```bash
docker run -d --name fvt -p 4200:80 \
  -e SERV_HOST=https://aegis.coevolution-project.eu \
  -e API_URL=/api/v1 \
  -e KEYCLOAK_URL=https://aegis.coevolution-project.eu \
  -e SRME=https://<srme-host>/dashboard.html \
  ghcr.io/coevolution-project-eu/coevolution-dash:latest
```

Open **http://localhost:4200/fvt/** (the trailing `/fvt/` is required).

For logins to work from `localhost`, the Keycloak client must allow this origin (see [Authentication](#authentication)).

### Building the image

```bash
docker build -t ghcr.io/coevolution-project-eu/coevolution-dash:<tag> .
docker push ghcr.io/coevolution-project-eu/coevolution-dash:<tag>
```

The `Dockerfile` uses a multi-stage build:

1. A Node stage compiles the Angular app for production under the `/fvt/` base path.
2. An Nginx stage serves the compiled files.
3. At startup, `envsubst` writes the environment variables into `assets/env.js`.

### Angular development server

Requires Node.js 18+, npm and the Angular CLI.

```bash
npm install
# set the variables in src/assets/env.js
ng serve
```

Open **http://localhost:4200/fvt/**.

## Authentication

Authentication is delegated to the **User and Credential Management** component (Keycloak, realm `coevolution`), as described in D6.2 Sections 3.1.4 and 4.1:

1. **User login.** The user signs in through the Dashboard. Keycloak validates the credentials and issues a signed JWT access token, valid for one hour.
2. **API security.** Every Dashboard call to the Orchestrator carries the token as `Authorization: Bearer <token>`. The Orchestrator verifies its signature, issuer and audience against Keycloak's public keys (`/realms/coevolution/protocol/openid-connect/certs`). Requests without a valid token are rejected with 401 or 403.
3. **Pilot access.** Pilot partner accounts (SIE, AVL, AVI) can only upload to their own assigned bucket. The Orchestrator enforces this.

### Keycloak client settings for a new deployment

| Setting | Value |
| --- | --- |
| Realm | `coevolution` |
| Client ID | `<client-id>` <!-- TODO: confirm --> |
| Valid redirect URIs | `https://<your-domain>/fvt/*` (and `http://localhost:4200/fvt/*` for local use) |
| Web origins | `https://<your-domain>` (and `http://localhost:4200`) |

New users need an account in the `coevolution` realm. Contact the Hub administrators to request one.

## Verifying the deployment

1. `kubectl get pods -l app=fvt` shows the pod as `Running` and `1/1` ready. The readiness probe checks `/fvt/`.
2. Opening `https://<your-domain>/fvt/` redirects to the Keycloak login page.
3. After login, the Dashboard home page loads.
4. The model list loads in the Monitoring View. This confirms that `SERV_HOST` and `API_URL` are correct and the token is accepted.
5. The SRME view displays the embedded SRME interface.

## Troubleshooting

| Symptom | Likely cause and fix |
| --- | --- |
| Blank page or 404 | The URL is missing `/fvt/`, or the Ingress path does not route `/fvt` to the `fvt` service. |
| Pod not ready | The readiness probe on `/fvt/` fails. Check `kubectl logs deploy/fvt` and confirm the image was pulled from GHCR (a private package needs an `imagePullSecret`). |
| Keycloak shows "Invalid redirect URI" | Add the Dashboard URL to the client's *Valid redirect URIs*. |
| Login loop or CORS errors | The Dashboard origin is missing from the client's *Web origins*. |
| Dashboard loads but no models appear | `SERV_HOST` or `API_URL` is wrong, or the Orchestrator rejects the token (401/403). Check the browser's Network tab. |
| SRME view is empty | `SRME` is unreachable, uses `http://` on an HTTPS page (mixed content), or the SRME server forbids framing (`X-Frame-Options` / `frame-ancestors`). |
| ConfigMap changes have no effect | Run `kubectl rollout restart deployment/fvt`, then hard-refresh the browser. |
